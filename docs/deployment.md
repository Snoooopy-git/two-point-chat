# 部署与回退 Runbook

本文件描述允许的生产流程，但不构成部署授权。每次部署仍需明确指定版本、环境和回退基线。

## 前置条件

- 已确认发布 commit 和 `vMAJOR.MINOR.PATCH` tag。
- CI 全部通过。
- 目标环境提供强 `JWT_SECRET`、`CHAT_DB_PATH` 和代码目录之外的 `BACKUP_DIR`。
- 当前数据库最近一次恢复演练有效。
- 已记录部署前 commit、数据库路径和回退版本。

## 标准流程

1. 检查目标、版本、维护窗口和回退基线。
2. 在代码变更和进程重启前执行一致性在线备份。
3. 验证备份数据库 `PRAGMA integrity_check` 结果为 `ok`。
4. 仅获取已确认的 tag；禁止从不确定分支部署。
5. 使用 lockfile 安装依赖。
6. 在目标 Linux 执行 `npm rebuild better-sqlite3`。
7. 执行完整质量门禁和前端构建。
8. 裁剪开发依赖时禁止 npm 写入 lockfile，并验证根目录与客户端 lockfile 未发生变化。
9. 以 PM2 单实例 fork 模式更新进程。
10. 验证健康检查、前端、关键 API 和数据库完整性。
11. 记录部署版本、备份、验证和剩余风险。

仓库中的 `deploy.sh` 只负责第 2、5–10 步。获取 tag、传输代码和选择环境必须在脚本之外经单独授权完成。

## 数据保护

- 禁止把 `chat.db*`、上传、日志、备份或生产 `.env` 放入发布包。
- 备份目录必须位于代码目录之外。
- WAL 模式下禁止用多条普通 `cp` 命令拼装“备份”。
- 使用 `npm run db:backup -- --source <db> --out-dir <dir>` 创建 SQLite 在线备份。
- 使用 `npm run db:recovery-drill -- --backup <file>` 执行隔离恢复验证。

## 失败与回退

- 构建或备份失败：停止，保持旧进程运行。
- 重启后健康检查失败：停止后续操作，收集 PM2/Nginx 日志。
- 代码回退只切换到预先确认的 tag，不自动执行数据库降级。
- 数据恢复属于独立高风险操作，必须重新确认备份、目标路径和数据损失窗口。
- 回退后重复健康、关键 API 和数据库完整性检查。

## 禁止事项

- 禁止直接运行未审阅的 `git pull && pm2 restart`。
- 禁止全量 tarball 覆盖生产目录。
- 禁止在未备份时执行迁移或重启新版本。
- 禁止在健康检查失败后继续部署。
